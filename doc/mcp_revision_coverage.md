## The rule

The dispatcher advances a document's revision by exactly one when a write handler reports that it began changing native state and the tool is not declared mutates_document false (automation_dispatch.cpp:488-517). A write that changes nothing returns the current revision. A write that fails after state changed is reported as partially_applied and still advances the revision. A write that fails before any change leaves the revision alone.

Every write carries expected_revision, so a stale call fails with revision_conflict before the handler runs (automation_dispatch.cpp:475-486). An exact retry with the same operation_id returns the stored outcome without running the handler again, even after later writes (automation_dispatch.cpp:386-415).

The revision is reported by the handler, not computed from content, so the table below checks it against reads: a successful call must advance it by one and change a read, and a call that changes no read must not advance it.

## Live undo and stale edits

Question: What does a stale edit see when live undo returns content to an earlier fingerprint?

Current behavior:

- The live fingerprint hashes the qualified metadata of the scene, the target and the undo history's change generation (automation_live_scene.cpp, snapshot and fingerprint). Undo, redo and every new history entry advance that generation (tundo.cpp), so the fingerprint after an edit and its undo differs from the one before the edit, although the content is the same.
- An edit that carries an earlier fingerprint is refused with stale_target (automation_live_scene.cpp, requireFresh). Nothing changes and no undo entry is added. The error's details give a reason and the current_fingerprint: content_changed when the qualified metadata differs from what the fingerprint covered (also for a fingerprint the editor did not issue), history_changed when the metadata is the same but the history moved, and target_replaced when the target's native parameter was replaced. The editor keeps a bounded record of the fingerprints it issued to tell these apart.
- A history change also clears the observed state and advances the observation serial (automation_live_scene.cpp, observeHistory). A history reset or a scene switch starts a new scene epoch, and an edit with the old epoch is refused with scene_changed (automation_live_scene.cpp, requireEpoch).
- Native tests in the live fixture (tests/mcp_live_history_test.cpp) cover an edit prepared before an undo and before a redo, the reasons for each, a retry with the reported current fingerprint, a replaced target and a fingerprint the editor never issued.
- The detached worker has no undo, so its revision only moves forward.

Options:

- Keep history-bound fingerprints: A fingerprint never returns to an earlier value. Every undo or redo forces a new inspection, even when content is identical. Cost: An agent loses a pending edit after a human undo that restored the same values.
- Make the fingerprint content-only: An edit built before an edit-and-undo pair is accepted after it. Cost: Reuses a former fingerprint, which the revision rule forbids, and cannot tell whether a redo branch was dropped or an owner was recreated under a new identity.
- Keep history-bound fingerprints and say why: Refuse as today, add a reason code and the current fingerprint to the error, and cover undo, redo and a stale edit with native tests. Cost: Needs a live contract amendment and tests.

Decision: Keep the history-bound fingerprint and add the reason and the current fingerprint to stale_target. A revision that returned to an earlier value would let an agent act on a state it never saw, and the extra detail removes the cost of re-inspecting. Implemented with the live protocol v2 handshake; the native tests for undo, redo and a stale edit are in tests/mcp_live_history_test.cpp.
